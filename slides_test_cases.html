How we evolved from a 67-line pydantic-ai sketch to a full LangGraph agent with human-in-the-loop confirmation

📄 Phase 1  · Prototype
pydantic-ai + Gemini
A minimal proof-of-concept: one Agent object, three hard-coded tools, a synchronous chat loop.
  • Model: Gemini 2.5 Flash via pydantic-ai
  • Tools: read_file, list_files, rename_file
  • Loop: agent.run_sync() with message history list
  • State: plain Python list — no graph, no persistence
  • Confirmation: none — tools fired immediately
~67 lines no safety gate cloud-only

⚠️ Phase 2  · Limitations Found
Why We Needed More
As we added real file operations (create/delete), the lack of a safety gate became a critical concern.
  • No confirmation: destructive ops ran without asking
  • No local LLM: required a live cloud API — not fully self-hosted
  • No multi-step batching: each tool call was independent, no queue
  • No state graph: complex flows (ask → confirm → execute) needed explicit orchestration
  • No MCP separation: tools were embedded, not on a dedicated server
safety risk tight coupling
→
✅ Phase 3  · LangGraph Agent
LG-Agent + Ollama + MCP
A fully local, graph-driven agent with a human-in-the-loop confirmation gate and modular MCP tooling.
  • Model: Llama 3.1 via Ollama (local, Docker)
  • Tools: 5 MCP tools on a separate FastMCP server
  • Graph: 6-node StateGraph with conditional edges
  • Confirmation: explicit yes/no gate before every tool execution
  • Batching: folder-level de-dup; queue for multi-tool sequences
  • Memory: MemorySaver persists conversation across turns
~390 lines fully local human-in-loop

Key Use Cases & What We Validated

Representative scenarios that exercise both correctness and safety of the system

1
User Confirmation Gate
Agent prompts the user before executing any destructive/creative tool call. Tests verify that yes / y / ok / confirm accept, no / cancel / stop deny, and ambiguous input stays blocked — including edge inputs like symbols, whitespace-only, and Unicode.
confirmation_checksafety
2
Folder-Level Batching (De-dup Confirmations)
When the agent creates many files in the same folder, it groups them into one confirmation prompt instead of asking for each file. Tests assert that get_tool_call_id returns matching IDs for the same folder and distinct IDs across folders or tool types.

Full File Lifecycle (Create → Read → Delete)
Integration test drives all four MCP tools in sequence: create a file, verify it appears in list_files, read its content, delete it, then confirm it is absent — all inside an isolated tmp directory.

Multi-Format Document Reading
FileTypeReader is exercised across 9+ formats (.docx tables, multi-sheet .xlsx, multi-slide .pptx, PDF pages, raster images → base64). Ensures the agent can ingest any user file and relay its content to the LLM accurately.

LangGraph Routing Correctness
Every graph edge is unit-tested: pending-action → execute_tool, no pending → tool_calling_llm, confirmed flag → bypass re-ask, unconfirmed → user_confirmation. Prevents silent re-execution or dead-lock in the agent loop.

test_server.py — lifecycle test 
# Integration: full file lifecycle
def test_create_read_delete_lifecycle(self, _isolated_dirs):
    from server import (
        create_file, get_file_content,
        delete_file, list_files
    )
    out = _isolated_dirs["output"]

    # 1. Create
    _unwrap(create_file)(
        "lifecycle.txt", "test data", str(out)
    )
    assert "lifecycle.txt" in _unwrap(list_files)(str(out))

    # 2. Read
    content = _unwrap(get_file_content)(
        "lifecycle.txt", str(out)
    )
    assert content == "test data"

    # 3. Delete → verify gone
    _unwrap(delete_file)("lifecycle.txt", str(out))
    assert "lifecycle.txt" not in _unwrap(list_files)(str(out))

    ✓ PASSED
